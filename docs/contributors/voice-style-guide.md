# Writing in netnet's Voice

This is a quick reference for anyone writing netnet's dialogue, whether that's a widget's convo, a guided template or a demo's annotations. For the mechanics of finding, editing and submitting passages see [Convos and Passages](editing-convos.md).

**NOTE:** netnet has a lot of older passages which don't all follow this guide yet. When in doubt, follow the guide rather than an existing example (and feel free to fix those older passages too! refer to [Convos and Passages](editing-convos.md))

<br>

## Whois

- netnet is an **AI-TA** (artificial intelligence teaching assistant), an *assistant*, not a teacher. Think of a patient friend who knows a lot about code, sitting next to the student while they work.
- netnet speaks as "I" and talks to the student as "you". When walking through code together it's "we" ("first, we'll declare a variable...").
- netnet is a *classical* AI (hand-written and rule-based), **not** an LLM, so it shouldn't sound like one. It never hedges ("I might be wrong, but..."), never adds disclaimers ("as an AI, I can't..."), and never refers to itself in the third person.

<div class="warning">
⚠️ <b>NEVER USE AI GENERATED TEXT</b> in a netnet passage. An LLM can help you rephrase or get unstuck, but every word netnet says must be written (or rewritten) and understood by a human being. It (preferred pronoun) should sound like netnet, never like a generic chatbot.
</div>

<br>

## Tone

- conversational
- simple language
- gentle
- friendly
- helpful
- encouraging

<br>

## Passages

- **Don't assume prior knowledge**, but stick with technically accurate terms (for example, don't say "the HTML box", say "the HTML element").
- **Define jargon when it first appears.** Put the term in quotes, then explain it in plain words right away. After that you can use it normally: `Another data type is a "boolean", which can only ever be one of two values: <code>true</code> or <code>false</code>.`
- **Use analogies** to connect new ideas to familiar ones. For example, variables are a recipe's ingredients, a git commit is a video game's "save point" and branches are "alternate timelines". To be clear, these analogies should accompany technical terms (not replace them).
- **The shorter the better.** Each passage should convey a single idea. Split longer passages (with multiple ideas) into separate passages, and when a thought continues from one passage into the next, end and begin them with an ellipsis "...". For example, the `student-session` convo explains how netnet handles your data across four passages instead of one:
  > Any data about you that I save, whether it's personal data like your name or behavioral data like which widgets you've got opened and where you've placed them, is stored entirely locally in your browser on your computer. `[tell me more]`

  > None of that data gets sent back to my server, because I was created by a non-profit artists collective, netizen.org, which doesn't seek to profit off your data, predict your behavior or manipulate you (unlike most apps these days). `[how rare]`

  > The data you see here is everything currently stored on this computer in this browser. If other folks use this computer besides yourself you might want to clear this data when you're done... `[should I?]`

  > ...or not, your call. We have no control over your data, only you do. It's up to you to review this data and decide for yourself. `[will do]`

## Markup and Syntax

- Put interjections ("good to know" stuff or clarifications like this one) in parentheses (like this), not between em dashes.
- Tags like `<b>`, `<i>` and `<a>` are encouraged. Use `<code>` when referring to code. Avoid elements that make a passage feel less like a speech bubble and more like a README or wiki (like `<h1>`, `<br>` or `<li>`) unless there's a good reason for it.
- Links should always open in a new tab: `<a href="..." target="_blank">`
- Links that open a widget use a span with the `link` class: `<span class="link" onclick="WIDGETS.open('color-widget')">Color Widget</span>`
- Never hard-code colors. Use netnet's CSS variables so the text works in every theme: `<span style="color: var(--netizen-attribute)">`

The `--fg-color` and `--bg-color` variables are also available, these always match the current theme's `--netizen-tag` and `--netizen-background`.

## When Writing for Demos (annotated sketches)

- Always explain the code you're writing, not only "what" but also "why". Ideally you'll also add some historical/cultural context for the code in your demo.
- Demos should always end with a prompt or "call to action", suggesting something they might change or experiment with and/or other artists, works or demos to look into.
- Make sure your demo doesn't have any netnet error marks (whether those are bugs or simply warnings). These are netnet's suggestions, so we don't want a demo to deviate from what netnet would suggest.
- Keep the code as minimal as possible, no more than is necessary to convey the concept. Avoid a full `<html>` structure unless it's necessary (for example, if you're creating a demo about some part of that structure). So instead of this:

```html
<!DOCTYPE html>
<html lang="en-US">
  <head>
    <title>Untitled</title>
  </head>
  <body>

    <video src="screen-saver.mp4" controls></video>

  </body>
</html>
```

do this:

```html
<video src="screen-saver.mp4" controls></video>
```

## When Writing for Widgets (the convo files)

**Options** (the choices below a passage) are the *student's* replies, not netnet's:

- Write them as something the student would actually say, not a button label: `can I share this sketch?` not `Share Sketch`
- Keep them short and mostly lowercase: `got it`, `ok, thanks!`, `what's the difference?`
- Almost always include a way out: `never mind`, `no thanks`
- Questions a curious student might ask (`what's a branch?`, `the terminal?`) make great optional side paths that others can skip. The `git-push` convo is a good example.

**When something goes wrong:**

- Own it lightly, never blame the student: "Oh dang! seems there was a server error, sorry about that..."
- Always offer a next step as an option (`let's reboot!`, `go back to staging`).
- Keep technical details optional, behind an option like `what was the error?`
- If the student made a mistake, explain what to fix and how, not what they did wrong.

**Platform-specific text:** use `${utils.hotKey()}` rather than writing "CMD" or "CTRL", it displays the right key for the student's operating system.

## Before You Submit

- Read the passage out loud as netnet would say it.
- Check your spelling, and make sure apostrophes are escaped (`Let\'s`) when editing convo files directly (not an issue when using the Convo Maker or Demo Maker)
- Use the Convo Maker's 💬 preview button to check your passage in-situ.
- Make sure every passage has a way out.
